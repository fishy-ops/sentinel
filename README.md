# Sentinel

Sentinel is a transaction fraud triage service with reproducible synthetic data and an authenticated transaction API.

## Quickstart

```sh
uv sync
make data
uv run python -m sentinel.api.keys create --scopes ingest,read --name local
make run
uv run pytest -q
```

Generated train, val, eval, and finetune files are written to `data/generated/`.
Set `SENTINEL_DATABASE_URL` to choose a SQLite database; the default is `sqlite:///./sentinel.db`. Send the printed key in `X-API-Key` when calling `/v1` endpoints. Set `SENTINEL_RATE_PER_SECOND`, `SENTINEL_RATE_BURST`, and `SENTINEL_MAX_BODY_BYTES` to adjust request limits.

## Detection and evaluation

```sh
make data train eval-flags
```

Training fits an IsolationForest without labels and a HistGradientBoostingClassifier with train-split labels. Validation labels select each threshold by F1. The eval split is used only to report transaction and episode metrics. Results and the precision–recall plot are in `evals/results/` and `docs/results/`; PR-AUC is average precision. Misclassified rows, including their features and reasons, are written to the ignored `evals/failures/flags.jsonl`.

The API uses named rules by default. Set `SENTINEL_MODEL_ARTIFACT=models/iforest.joblib` to combine rules with both trained models. Each flag records its reasons, score, and model version. The model files are generated by `make train`; their JSON sidecars record the feature list, threshold, training data hash, and library version.

## Analyst explanations

Set `SENTINEL_LLM_BASE_URL` (default `http://localhost:11434/v1`) and `SENTINEL_LLM_MODEL` (default `qwen2.5:7b`) to select a local OpenAI-compatible chat endpoint. `POST /v1/flags/{id}/explain` with a read-scoped key runs the analyst and stores its tool trace, grounding report, and latency. `GET /v1/flags/{id}/explanation` returns the latest result, including failures and ungrounded claims. The analyst can only read the flagged account's data. Run `uv run python -m sentinel.agent.explain --flag-id N` against the configured database for a local inspection.

`GET /v1/audit/verify` returns the count and head hash of the chain before its own audit entry is appended. Store both outside the database to detect a truncated tail during a later check.

## Explanation evaluation and security checks

With a local model available, run `make eval-explanations` to sample flagged transactions from the eval split and score report validity, grounding, tool use, decisions, and adversarial cases. Use `uv run python -m evals.run_explanations --help` for model, sample size, and revision options. Results are in `evals/results/explanations.{json,md}` and `docs/results/grounding.png`; cached runs and failure records are ignored by Git.

Run `make redteam` for in-process API and tool-boundary checks. Add `--with-model` to `uv run python -m evals.redteam` to include the live prompt-injection case. The suite writes `evals/results/redteam.{json,md}` and exits nonzero if any attack fails.
